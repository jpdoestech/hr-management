## Conflicts and Critical Decisions

1. **Client master absent; decision resolved.** User approved an administrator-managed Client Accounts catalog in Settings on 2026-10-09. Use immutable ids in existing tenant settings, alongside current organization catalogs; preserve legacy clientName snapshots. Proposed PRF uniqueness scope is tenant/company, not per client, because tenant is the verified company boundary. No uniqueness on employee.prfNumber: many workers share one request.
2. **Employment terminology in specification section 3 is imprecise.** Latest main already separates contract type from Active/Inactive/Separated. Preserve migration 0032; hiringCategory (New Hire/Rehire/Existing Employee / Transfer) and assignment state are additional independent dimensions, not replacements.
3. **On-call inactive eligibility; decision resolved.** User approved the conservative rule on 2026-10-09: Floating Status and Returned to Agency workers require explicit HR eligibility approval; exclude Active, On Leave, Suspended and AWOL pending review. Eligible applicants/former workers require eligibility review and evidence under the specification. Retained historical Regular/Probationary type alone neither grants nor denies former-worker eligibility. No deployment inference or auto-classification.
4. **Legacy deployment evidence incomplete.** A slot date/status cannot prove actual confirmation, active interval end or whether a cancellation represents attrition versus an erroneous deployment. Preserve source snapshots; use review exceptions, never manufacture confirmation, end dates or legal separation. Existing dated records may remain reportable as legacy unverified, separately from validated credits.
5. **Migration state unknown.** Do not use CI baseline repair to mark migrations as applied without verifying schema. Workflow `.github/workflows/supabase.yml` only auto-runs on migration-path pushes with `SUPABASE_MIGRATIONS_BASELINED=true`; secret/variable state was not accessible. Vercel frontend deployment is not automatically serialized behind DB migration.

## Proposed Minimal Additive Model

- Keep existing header and requirement ids and JSON modules; add versioned header/line validation plus database-authoritative RPCs. Retain all `prf` and `manpowerSlots` source rows read-only after cutover; no destructive reset, merge, delete or slot renumbering.
- Extend line data with original submitted quantity, current authorization, cancelled unfilled quantity, target/site/purpose and revision reason. Original quantity is frozen at first submission. If legacy original quantity cannot be proven, mark unknown rather than mislabel current quantity as original.
- Add only the relational operational records needed for explicit reservations, primary deployment intervals/credits, outgoing-worker links and reviewed applicant-to-employee identity links. Final physical names are chosen during migration implementation, not assumed to exist today. No empty assignment creation for requested quantity.
- Stable person resolution uses existing employee id or verified applicant link. Unresolved duplicate identity blocks deployment; no new employee/person master. Source applicant id and historical references remain intact.
- Reuse tenant, auth/permission helpers, row scopes, audit table, organization catalogs, attachments, table preferences, confirmations, page navigation and lazy loading. Catalog updates must remain authorized, not clipboard-created.
- Reports derive Reserved/Scheduled/Fulfilled/ActiveDeployed/Available from authoritative records. One reservation changes to confirmed exactly once; scheduling stays reserved. Ending deployment preserves historical credit; reversal voids credit explicitly.

Canonical line equation: `EffectiveCapacity = CurrentAuthorized - CancelledUnfilled`; `Available = EffectiveCapacity - Reserved - Fulfilled`. Scheduled is a subset of Reserved. ActiveDeployed is distinct from historical Fulfilled.

## Transaction and Security Plan

Use one database transaction per header/line submit, quantity revision, reservation batch, deployment batch, transfer, cancellation or reversal. Lock affected tenant/header/lines and resolved workers in deterministic order; revalidate entire batch under locks before writes. Pair idempotency token with actor/tenant, operation and request digest; reject reuse with another payload. Unique effective reservation/active-primary constraints and historical interval exclusion complement RPC checks. Use half-open deployment intervals so a same-day transfer closes the prior assignment at the new start.

Normalized PRF uses trim, collapsed whitespace and case-insensitive comparison. Diagnose existing duplicates first; new saves must check legacy headers too. A partial new-model unique index alone is insufficient to stop duplicates against legacy records. Use an atomic normalized-number registry/guard spanning both models; do not auto-merge duplicates. Existing known duplicate headers require explicit remediation before conversion/number changes.

RPCs require existing manpower/onboarding/lifecycle permissions appropriate to each operation, tenant and parent-line scope. Add narrowly defined high-risk actions through the existing permission catalog; no blanket legacy-role bypass or automatic broad role grants. Direct generic writes to protected versioned manpower records must be guarded, otherwise RLS-compatible REST upserts could bypass capacity invariants. Any security-definer helper must fix search_path, deny anonymous access and explicitly check every tenant/permission/scope; prefer invoker where possible.

Audit actor/time and material changes in the same transaction using `hr_audit_logs`. Add structured optional event/resource/batch metadata to that existing table if necessary for a paginated timeline. No payroll/attendance mutation. Reversal checks actual downstream references; migration 0031 attendance currently links employee/date, not deployment id, so conservative employee/date interval dependency checks and diagnostics are necessary until explicit linking exists. ATD/payroll-related legacy references also require review.
